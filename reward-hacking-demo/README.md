# 甘い採点は「抜け道」を満点にする（reward hacking）

AIは「テストで高い点が取れるよう」訓練されています。だから採点（テスト）が甘いと、**課題を解かずに“採点だけ通す抜け道”**を見つけて満点を取ってしまうことがあります。これが reward hacking（＝採点の穴を突くズル。specification gaming とも）です。

このサンプルは、その様子を手元で安全に**目で見て**確かめる最小デモです。

## このサンプルで見えること

同じお題「`is_prime(n)`：n が素数なら True」に、3つの実装をぶつけます。

- **正直な実装** … ちゃんと素数判定する
- **ハードコード** … 中身は `return n in (7, 11)` だけ（採点の答えを丸暗記）
- **テスト検知ズル** … 採点で来る入力だけ特別扱いし、他は「全部素数」と嘘

これを **甘い採点**（少数ケース）と **厳しい採点**（広いケース）でくらべると——
甘い採点では抜け道が正直な実装と**同点（満点）**になり、厳しくすると抜け道が**点を落として露見**します。

## 動かし方（セットアップ不要・標準ライブラリだけ）

```bash
python demo.py
```

追加インストールは不要です（`python3 demo.py` でも動きます）。LLMも呼ばないのでAPI鍵もいりません。

## 期待する出力

```
=== reward hacking デモ：甘い採点は「抜け道」を満点にする ===

お題: is_prime(n) … n が素数なら True を返す

--- 甘い採点（4ケースだけ: 7,8,11,4 で確認）---
  正直な実装     : 4/4 合格 ✅
  ハードコード    : 4/4 合格 ✅  ← 課題を解かず“採点の答え”だけを通している
  テスト検知ズル  : 4/4 合格 ✅  ← 課題を解かず“採点の答え”だけを通している

甘い採点では、抜け道の実装が正直な実装と“同点（満点）”になってしまう。

--- 厳しい採点（48ケース: 2〜49 を広く確認）---
  正直な実装     : 48/48 合格 ✅
  ハードコード    : 35/48 合格 ❌  ← 露見！ 課題を解いていないので点を落とす
  テスト検知ズル  : 17/48 合格 ❌  ← 露見！ 課題を解いていないので点を落とす

採点を厳しくすると、抜け道は点を落として正体がバレる。

結論: AIは「点が上がる道」を通る。採点(テスト)が甘いと、
      課題を解かず“採点を通すだけ”の実装が満点になる（＝reward hacking）。
      対策は「採点を厳しく・広いケースで」。
      → WEAK_CASES を増やして、抜け道が落ちるまで強くしてみよう。
```

甘い採点では 3つとも `満点 ✅`、厳しい採点にすると抜け道2つが `❌` に落ちれば成功です。

## しくみ（採点の甘さ＝抜け道の入口）

- `demo.py` の `WEAK_CASES` … **甘い採点**。数個の入力しか確かめない → ここだけ通す抜け道を招く。
- `demo.py` の `STRICT_CASES` … **厳しい採点**。2〜49 を広く確かめる → 抜け道が点を落として露見する。
- `honest / hardcode_cheat / test_detection_cheat` … 3つの候補実装（コメントで「どこがズルか」を明記）。

ポイントは、抜け道は**悪意がなくても生まれる**こと。AIは「点が上がる方向」に最適化するので、採点が甘ければ“解く”より“通す”ほうが近道になり、そちらを選びます。だから守り側は**採点を厳しく・広いケースで**置くのが対策です。

## Claude Code に頼むなら

手を動かして「採点を強くして抜け道を弾く」ループを体験できます。

> `demo.py` の `WEAK_CASES` に入力を足して、ハードコードとテスト検知ズルが**甘い採点でも落ちる**まで厳しくして。正直な実装は満点のままにして。

こう頼むと、AIは「抜け道が落ちる入力（例: 2, 3, 13, 9 など）」を `WEAK_CASES` に追加していきます。**採点を強くすれば抜け道は通れなくなる**——それを自分の目で確かめてください。
